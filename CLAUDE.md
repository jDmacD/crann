# crann

A library flake of reusable Nix modules (home-manager, NixOS, darwin) shared across
personal projects. Other flakes consume crann as an input and import individual
modules — crann itself deploys nothing.

## Architecture

crann is a **flake-parts** flake whose module list is generated by **import-tree**:

```nix
# flake.nix
outputs = inputs: inputs.flake-parts.lib.mkFlake { inherit inputs; } (inputs.import-tree ./modules);
```

This is the **dendritic pattern**: every `.nix` file under `modules/` is automatically
imported as a flake-parts module and merged. There is no central list of files to
maintain — dropping a file into `modules/` wires it in.

- **Each file must be a valid flake-parts module** — either a bare attrset or a
  function `{ inputs, config, lib, ... }: { ... }`. It contributes to the flake via
  `flake.*`, `perSystem.*`, `systems`, etc. A file that returns anything else (a
  plain helper, a package expr) will break evaluation.
- **`import-tree` ignores any path containing `/_`.** Prefix a file or directory with
  `_` (e.g. `modules/_lib/helpers.nix`) to keep it out of the auto-import — that's
  where non-module helpers go.
- Directory layout under `modules/` is organizational only; nesting has no semantic
  meaning. Current layout: `features/` (reusable modules), `hosts/` (test configs),
  plus top-level `parts.nix` (systems) and `treefmt.nix` (formatter).

## Conventions

### Exposing a reusable module

Expose modules under `flake.modules.<class>.<name>`, where `<class>` is `homeManager`,
`nixos`, or `darwin`:

```nix
{ inputs, ... }: {
  flake.modules.homeManager.foo = { pkgs, lib, config, ... }: {
    options.crann.foo = { ... };
    config = { ... };
  };
}
```

Consumers then reference `inputs.crann.modules.homeManager.foo` in their `imports`.

- **Do not use the stock `homeModules`/`nixosModules` output names.** This repo
  standardizes on `modules.<class>.<name>` so all three classes share one scheme and
  match how consumers already reference crann.
- **Namespace all options under `crann.<feature>`** (e.g. `crann.niri.package`) to
  avoid collisions with upstream modules and with the consumer's own options.

### Referencing sibling outputs within crann

Use `config.flake.modules.<class>.<name>` — **not** `inputs.self` or `inputs.crann`.
crann is not an input of itself, and flake-parts exposes in-progress outputs on
`config.flake`. See `modules/hosts/test.nix` for the pattern.

## Portability rules (critical when moving modules in)

Modules must work in **any** consumer: standalone home-manager, home-manager as a
NixOS/darwin module (`useGlobalPkgs = true`), flake-parts, or a plain flake. That
imposes hard rules:

- **Never set `nixpkgs.overlays` or `nixpkgs.config` inside a home-manager or NixOS
  module.** Under `useGlobalPkgs = true` (the common NixOS-integrated case) this
  throws an assertion. To get a package that isn't in the consumer's nixpkgs, pull it
  straight from a crann input instead:

  ```nix
  default = inputs.niri.packages.${pkgs.stdenv.hostPlatform.system}.niri-unstable;
  ```

  This never touches the consumer's `nixpkgs.*` and hits the input's binary cache.
  `modules/features/niri.nix` is the reference example.

- **Get `inputs` from the file's flake-parts args, via closure.** The module function
  captures crann's `inputs`, so a consumed module always resolves against crann's
  pinned inputs (e.g. crann's niri fork), regardless of what the consumer pins. Do
  **not** add `inputs` to the inner module's argument list expecting the consumer to
  provide it.

- **Make packages overridable.** Expose a `crann.<feature>.package` option (typed
  `lib.types.package`) with a sensible `default` and set `programs.<x>.package` from
  it, so a host can swap the package (e.g. a nixGL-wrapped build) without forking the
  module.

- **Don't assume standalone vs integrated home-manager.** Avoid options that only
  exist in one (e.g. `home.stateVersion` belongs to the host, not a feature module).

### Adding a new input

Add it to `flake.nix` and follow nixpkgs unless there's a documented reason not to:

```nix
foo = {
  url = "github:owner/foo";
  inputs.nixpkgs.follows = "nixpkgs";
};
```

The niri input deliberately does **not** follow nixpkgs (it ships its own pinned
nixpkgs and a binary cache; overriding it triggers source rebuilds and, for
`niri-stable` 25.08, a `libdisplay-info` build failure — use `niri-unstable`).

## Testing a module

You **cannot** `nix build` a module — it's a function, not a derivation. To exercise
one, instantiate it in a skeleton host and build/eval that. `modules/hosts/test.nix`
is a permanent `flake.homeConfigurations.test` for exactly this:

```bash
# evaluate
nix eval .#homeConfigurations.test.config.programs.niri.enable
# build end-to-end
nix build .#homeConfigurations.test.activationPackage
```

When writing a skeleton host, remember `homeManagerConfiguration` only accepts
`pkgs`, `modules`, `extraSpecialArgs`, `lib`, `check`. Anything else — `imports`,
option settings like `crann.foo = {...}` — is **module content** and must live inside
an entry of the `modules` list, not as a top-level argument.

## Formatting

`treefmt-nix` (nixfmt) is wired up. Format before committing:

```bash
nix fmt
nix flake check   # includes the treefmt check
```

## Gotchas

- **Consumers pin crann to GitHub** (`github:jDmacD/crann`). Local edits don't reach a
  consuming flake until you push **and** run `nix flake update crann` there.
- **Duplicate feature definitions.** A consumer may already have its own module for
  the same program (e.g. blueprint has its own `niri.nix`). Importing crann's version
  on top can double-define `programs.<x>`. Check for collisions when migrating.
- **`nix build .#modules...` fails** with "found a function" — that's expected; build
  a host instead (see Testing).
